## 一、语音（TTS）领域术语

### TTS（Text-to-Speech，文本转语音）
给定一段文字，让机器生成对应的人声朗读。本项目就是研究"如何把一个开源 TTS 模型微调成你要的声音"。

### ASR（Automatic Speech Recognition，自动语音识别）
TTS 的反向任务：给音频出文字。在 TTS 微调里，ASR 有两个用途：一是给训练音频自动打文字标注（转录），二是评估合成语音的"内容准确度"（用 ASR 听合成结果，看文字对不对，即 WER）。

### 语音编解码器 / Codec（编码器-解码器）
把连续的声音波形压缩成一串离散"数字编号"（token），也能从编号还原回声音。
- **编码（encode）**：波形 → 一串数字编号（给训练用）。
- **解码（decode）**：数字编号 → 波形（生成/播放用）。
- 类比：就像把图像压缩成 JPEG，再从 JPEG 还原出图像。

### Tokenizer（分词器/编码器）
在 TTS 语境里，"tokenizer"通常指语音 codec（把声音编成 token 的工具）。注意它和 NLP 里"把文字切成词"的文本 tokenizer 是两回事——本项目里 `Qwen3TTSTokenizer` 是**语音**编码器，不是文字分词器。

### 语义 token vs 声学 token
- **语义 token**：编码"说了什么"（语言内容），丢掉音色细节。适合给语言模型理解语音。
- **声学 token**：编码"怎么说的"（音色、环境、细节），能高保真还原声音。
- Qwen3-TTS 用一个统一 codec 同时编码两者（多码本，见下）。

### Codebook（码本）
一组固定大小的"编号池"。比如某 codec 有 16 个码本，每个码本 2048 个编号。每帧（每 1/12.5 秒）的声音，被表示成"从这 16 个码本里各挑 1 个编号"——即每帧得到 16 个数字。

### 多码本（Multi-codebook）
一帧声音用多个码本同时表示（Qwen3-TTS 用 16 个）。码本越多，信息越丰富、音质越好，但模型要预测的 token 也越多、越难训。这就是"多码本 LM 架构"。

### 帧率 / FPS（12Hz / 25Hz）
每秒处理多少帧。Qwen3-TTS-Tokenizer-12Hz = 每秒 12.5 帧（约 12Hz）。帧率越低，每帧携带信息越多、序列越短、生成越快；这是 Qwen3-TTS 低延迟的关键之一。

### 自回归（Autoregressive, AR）vs 非自回归（Non-AR）
- **自回归（AR）**：一个 token 一个 token 往后生成，后面的依赖前面（像打字）。
- **非自回归（Non-AR）**：一次并行生成多帧，不一个个等（如 SoundStorm/MaskGCT）。
- **两个目标模型都是 AR**（官方 README 均 `Generation Mode: Purely Autoregressive`），且**都用 Depth Transformer 建模残差码本的层间依赖**（仅码本组织/调度不同）：
  - **Qwen3-TTS**：多码本 AR-LM。**Talker**（Qwen3）自回归预测码本 0，**Code predictor**（深度 Transformer）预测码本 1-15（16 码本，RVQ）。
  - **MOSS-TTS-Local-Transformer-v1.5**：AR **时间同步**——逐时间帧预测该帧全部 RVQ 层 + Depth Transformer 建模层间依赖（底座 Qwen3-4B，12 RVQ 层）。"Local"指时间同步/局部调度，**不是"非自回归"**。
- LoRA 接入位置两者相通（q/k/v 等线性层）；loss 均按各自码本组织定制。⚠️ Qwen3 实际是 **2 段式**（`CE(码本0) + 0.3×CE(码本1-15)`，不是 16 路并行 CE），详见 `docs/05` 第 3/5 节。

### 参考音频 / Reference Audio
做"声音克隆"时，你给模型一小段目标人声（参考音频），模型提取说话人特征，生成新文字时模仿这个音色。Qwen3-TTS-Base 就是这么用的（3 秒克隆）。

### 零样本（Zero-shot）克隆
不训练，只靠一段参考音频直接克隆出音色。Qwen3-TTS-Base 出厂就支持。本项目的微调是它的进阶：用少量数据训练，让音色更稳、更像、更可控。

### 流式生成 / Streaming
边生成边播放，不用等整句合成完。Qwen3-TTS 用"双轨流式"做到首包延迟低至 97ms。微调阶段一般不碰流式逻辑，只训主干。

## 二、微调（Fine-tuning）领域术语

### 预训练 vs 微调（Pre-training vs Fine-tuning）
- **预训练**：从海量通用数据里训出基础模型（厂商做，算力巨大）。
- **微调**：在基础模型上，用你的少量数据再训，让它在特定任务/音色上更强。本项目做的就是这个。

### SFT（Supervised Fine-Tuning，监督微调）
有标准答案的微调：给"输入文字 → 对应语音 token"的成对数据，让模型学。本项目就是 SFT（不是后训练的偏好优化）。

### 全量微调（Full Fine-Tuning）
更新模型所有参数。效果可能最好，但显存占用大（要存所有参数的梯度/优化器状态）。1.7B 模型全量微调在单卡上吃力。

### LoRA（Low-Rank Adaptation，低秩适配）
不全量改模型，只在关键层旁挂一个"小补丁"（两个小矩阵 A、B，秩 r 很小如 8/16），只训这个小补丁。
- **好处**：可训参数减少 99%，显存大幅下降，单卡可训大模型；补丁文件小（几十 MB），可随时切换/合并。
- **代价**：理论上略逊全量微调，但实践中差异通常很小。

### QLoRA
LoRA + 4bit 量化基座模型（把原模型压成 4bit 存），进一步省显存。
- **关键约束**：4bit 量化靠 `bitsandbytes` 库，**该库只支持 NVIDIA CUDA，昇腾 NPU 用不了**。所以本项目走 **bf16 的普通 LoRA**（不用 QLoRA）。

### LoRA 超参
- **rank（r）**：补丁的"秩"，越大容量越大、也越易过拟合。常用 8/16/32。
- **alpha**：缩放系数，控制补丁影响强度（实际作用 = alpha/r）。**必须随 r 缩放**，常用 2~4 倍 r；案例1 固定 alpha=16 导致 r 越大反而越弱，是反面教训。
- **target_modules**：给哪些层挂补丁。Transformer 线性层通常是 `q_proj,k_proj,v_proj,o_proj`（注意力）+ `gate_proj,up_proj,down_proj`（前馈网络 MLP）。MOSS 官方脚本挂这 7 类；Twinkle 可直接写 `'all-linear'`。
- **adapter**：就是那个 LoRA 补丁本身。训练完保存的文件叫 adapter。

### bf16 / fp16 / fp8（数值精度）
模型参数用什么精度存。bf16=半精度（2 字节），比 fp32（4 字节）省一半显存，数值范围还够大，是当前主流。昇腾 910B 原生支持 bf16，本项目用它。

### 梯度累积（Gradient Accumulation）
显存小、batch 装不下时，把一个大 batch 拆成多次小 batch 前向，梯度先攒着不更新，攒够 N 次再一起更新——等效大 batch。常见 `batch-size 1, grad-accum 16`（每次算 1 条、攒 16 条算一次更新）。

### 学习率（Learning Rate, lr）、warmup、weight decay、grad clipping
- **lr**：每步更新多大步子。太大发散，太小学不动。LoRA 常用 1e-4 量级；全量SFT 常用 1e-5。
- **warmup**：开头用小学习率慢慢升到目标值，避免一上来就震荡。可按步数（如 100 步）或按比例（如 warmup_ratio 0.03）设。
- **weight decay**：对参数加一点正则惩罚，防过拟合。案例2（全量SFT）用 0.1；LoRA 常用 0.01~0.1。
- **grad clipping（max-grad-norm）**：梯度太大时截断（如 >1.0 就缩到 1.0），防训练爆炸。常 1.0。

### Epoch / 训练步数（train_iters）
把全部训练数据过一遍叫一个 epoch。也可按"步数"（train_iters）计，案例2 用 train_iters=10000。TTS 易过拟合，靠 val WER 早停，不盲调 epoch。

### Checkpoint（检查点）
训练到某步把模型/优化器状态存盘的快照。崩了能从最近 checkpoint 恢复。按 val WER 选 best，而非 last。

### 过拟合（Overfitting）
模型把训练数据"背"下来了，但泛化变差（换新文字合成质量下降）。TTS 微调尤其要小心：数据少时很容易把音色训死。案例1 因 train=dev 看不出过拟合，是反面教训。

## 三、训练框架/库术语

### Twinkle（本项目框架层）
modelscope 出的训练框架，**本项目框架层**（非裸 HF 四件套）。要点：
- **本方主导**：核心贡献者含招商银行开源技术团队；客户也将使用。成果可直接 PR 回本方框架。
- **原生支持昇腾 NPU**：通过 `kernelize` 用 CANN+FLA 融合内核与 fused-CE，不必自己配 torch-npu 细节。
- **原生支持 LoRA**：`model.add_adapter_to_model(name, lora_config)`；全量SFT 则不调用此方法。
- **组件化**：Dataset/Template/Preprocessor/InputProcessor/Model/Loss/Metric/Reward 等可插拔。
- **现无 TTS 支持**：支持文本 LLM 与多模态，但不支持 TTS。本项目要为它新增 `TTSMultiCodebookProcessor`+`TTSMultiCodebookLoss`——核心扩展点。
- 关键 API：`twinkle.initialize(mode, global_device_mesh)`、`TransformersModel`、`DataLoader`、`model.forward_backward/clip_grad_and_step/save`、`CLI.from_args()`。

### DeviceMesh / kernelize（Twinkle 专属）
- **DeviceMesh**：描述卡拓扑的对象。单卡用 `DeviceMesh.from_sizes(fsdp_size=1, dp_size=1)`；多卡调 fsdp_size。FSDP=把模型切片分摊到多卡。
- **kernelize(model)**：给模型套 NPU/CUDA 内核融合（CANN+FLA 高效注意力、fused linear CE 跳过 logits 物化省显存）。设 `TWINKLE_TORCH_BASELINE=1` 可回退纯 torch 基线排障。
- **Preprocessor/Trajectory/Message**：Twinkle 数据组件。自定义 `Preprocessor` 子类把原始数据转成训练格式；多模态用 `Trajectory`+`Message(role,content,images=[])`，TTS 仿此模式自定义。

### transformers / peft（Twinkle 内部库，非框架层）
Twinkle 内部基于它们，本项目不直接当框架层用：
- **transformers**：模型加载与生成 API；Twinkle 的 `TransformersModel` 封装它。
- **peft**：LoRA 实现（`LoraConfig`）；Twinkle 的 `add_adapter_to_model` 接入。

### trl / accelerate（已被 Twinkle 取代）
曾考虑用 TRL 的 `SFTTrainer` 与 accelerate 做设备/精度/梯度累积，框架层改用 Twinkle 后不再单独使用——这些职责由 Twinkle 的 `TransformersModel` 训练循环 + `DeviceMesh` + `kernelize` 吸收。

### datasets / manifest（数据清单）
训练数据组织成清单（jsonl）：每行一条"音频路径 + 文字 + 元信息"。本项目 manifest 含 `audio`/`text`/`ref_audio`/`audio_codes`/`language`（Qwen3：ref_audio 保留路径不预编码，audio_codes 是目标音频 `[T,16]`），由官方 tokenizer 预编码（见 `tts-data-pipeline` skill + `docs/05`）。MOSS 用 `moss_tts_train.jsonl` + `tokenized/` 目录，格式可借鉴。

### wandb / tensorboard
训练过程可视化工具，记录 loss 曲线等。可选。

### 为什么不用 unsloth / LLaMA-Factory
- **unsloth**：靠 Triton（NVIDIA 专用编译栈）加速，**昇腾 NPU 不支持**。
- **LLaMA-Factory/Axolotl**：配置式通用微调框架，**原生不支持 TTS 的多码本/局部 Transformer 训练格式**。

## 四、昇腾 NPU 术语

### NPU（Neural Processing Unit，神经网络处理器）
华为自研 AI 芯片，对标 NVIDIA GPU。本项目用 **昇腾 910B**。

### 910B
昇腾第三代训练芯片，大显存 HBM，单卡能跑 1.7B 级模型 bf16 LoRA。用户倾向单卡训练（哪怕时间翻倍），因此方案默认按单卡设计。

### CANN（Compute Architecture for Neural Networks）
昇腾的底层软件栈（类似 NVIDIA 的 CUDA + cuDNN）。装驱动/CANN 是跑 NPU 的前提。

### torch-npu（PyTorch NPU 适配）
华为提供的 PyTorch 插件，让 PyTorch 代码能跑在昇腾上。Twinkle 内部基于 transformers/peft 等纯 PyTorch 库，装了 torch-npu 后这些库可在昇腾跑——这是 Twinkle 能在昇腾可用的根本原因。

### MindSpeed / MindSpeed-MM
华为更上层的训练加速库 / 多模态训练套件（含并行、融合算子、FSDP）。同事的 MOSS-TTS-Delay 案例用它（见 `cases/`）。**本项目仅作备选**：仅当将来目标改成 MOSS-TTS-Delay 或要多卡全量SFT 才考虑。

### "纯 PyTorch 栈为何能在昇腾跑"
因为 torch-npu 把 PyTorch 算子映射到了 CANN；Twinkle 基于纯 PyTorch 故可在昇腾跑；而 unsloth 依赖 Triton（CUDA 专用），映射不过去——这就是"能用 Twinkle/transformers/peft，不能用 unsloth"的本质。

## 五、评估术语

### WER（Word Error Rate，词错率）
用 ASR 听合成语音，对比应读文字，算错误比例。越低越好。是衡量"内容准不准"的头号指标。Qwen3-TTS 技术报告里大量用 WER 对比各模型。

### 说话人相似度（Speaker Similarity, SIM / SS）
合成语音和参考音色在声纹上有多像。用专门模型算余弦相似度，0~1，越高越像。衡量"像不像目标人声"。

### UTMOS / MOS
主观/客观语音质量分。UTMOS 是自动打分模型；MOS 是人听后打分（5 分制）。越高越好听。

### PESQ / STOI
传统语音质量指标：PESQ 评听感质量，STOI 评可懂度。codec 评测常用。
