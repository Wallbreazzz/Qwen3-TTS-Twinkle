# 总体方案：昇腾 NPU · Qwen3-TTS / MOSS-TTS · LoRA SFT（基于 Twinkle）

> 本项目"地图"，写给不熟悉微调和语音的人：每步每词都解释。
> 术语详见 `docs/01-术语表与基础概念.md`（下称"术语表"）。

---

## 1. 项目要做什么（一句话）

在**昇腾 910B NPU** 上，用 **Twinkle 框架 + LoRA 微调（SFT）** 把开源 TTS 模型 `Qwen3-TTS-12Hz-1.7B-Base` 和 `MOSS-TTS-Local-Transformer-v1.5` 改造成目标音色/语种语音合成模型，并跑通"数据→训练→评估→部署"闭环；过程中为 Twinkle **新增 TTS 训练组件**并回流本方框架。

> 名词速记：**TTS**=文本转语音；**NPU**=华为 AI 芯片；**LoRA**=只训小补丁的省显存微调；**SFT**=监督微调；**Twinkle**=modelscope 出的训练框架，本方团队主导、客户也将用。

---

## 2. 两个目标模型
- **Qwen3-TTS-12Hz-1.7B-Base**（阿里）：多码本 AR-LM，底座 Qwen3。10 语种、3 秒零样本克隆。官方 `qwen-tts` 包给推理 + 语音 tokenizer（`Qwen3TTSTokenizer`，可编码音频为训练 token）；**官方仓库自带 `finetuning/`（`sft_12hz.py`+`dataset.py`+`prepare_data.py`，全量 BF16 SFT）**，是本模型训练/loss 的镜像源。架构实为 **2 段式**：Talker(AR 预测码本0) + Code predictor(深度 Transformer 预测码本1-15)，loss=`CE(码本0)+0.3×CE(码本1-15)`，详见 `docs/05`。
- **MOSS-TTS-Local-Transformer-v1.5**（复旦 OpenMOSS/MOSI.AI）：**自回归（AR）**，时间同步 RVQ 帧生成 + Depth Transformer 建模层间依赖（"Local"指时间同步/局部调度，非"非自回归"），底座 Qwen3-4B，48kHz 立体声、12 RVQ 码本。官方 `OpenMOSS/MOSS-TTS` 仓库**自带 v1.5 专属 finetuning**（`moss_tts_local_v1.5/finetuning/`，全量BF16 SFT），**作两模型对比用**（Qwen3 以自带 `sft_12hz.py` 为准）。

> 两模型都是 AR（仅码本组织与调度不同：Qwen3=逐码本、MOSS=逐帧同步+Depth Transformer），LoRA 接入位置相通，loss 镜像各自官方脚本。

---

## 3. 为什么用 Twinkle（框架层决策）
经本方训练专家确认，框架层定为 **Twinkle**（`github.com/modelscope/twinkle`）。理由：
1. **本方主导**：核心贡献者含招商银行开源技术团队，贡献者就在工位旁。
2. **客户将使用**：与客户后续技术栈一致。
3. **原生支持昇腾 NPU** ✅（CANN+FLA via `kernelize`、fused-CE，无需自己配 torch-npu 细节）。
4. **原生支持 LoRA**（`model.add_adapter_to_model`）与全量 SFT、FSDP2、多卡。
5. **支持 Qwen3 系列**（Qwen3-TTS 底座即 Qwen3，可作 `TransformersModel` 加载）。

> **重要事实**：Twinkle 现支持文本 LLM 与多模态，**尚无 TTS 支持**。本项目要为它**新增 TTS 训练组件**（多码本 `Preprocessor`+`Loss`）——这是核心扩展点，也是回流本方框架的价值产出。

### 框架层变更说明（相对上一版）
上一版用 `transformers+peft+accelerate+trl`（HF 四件套）。现改为 Twinkle（内部仍用 transformers+peft+FSDP2，但封装为标准化组件，并带 NPU 内核融合）。**弃用 unsloth**（CUDA-only）、**弃用 LLaMA-Factory**（不支持 TTS 架构）、**trl 退场**（被 Twinkle 训练循环取代）。

---

## 4. 为什么是 LoRA SFT（而非别的）
- 不做全量微调：单卡显存吃紧且易过拟合训死音色。
- 不做后训练（DPO/GRPO/RLHF）：用户明确只做 SFT。
- 不用 QLoRA：4bit 靠 bitsandbytes（仅 CUDA，昇腾不支持）；910B 大显存跑 bf16 LoRA 足够。
- 结论：bf16 + LoRA 单卡（用户倾向单卡哪怕时间翻倍）。

---

## 5. 硬件约束：昇腾 910B 带来的取舍
昇腾无 CUDA/Triton：
| 候选 | 910B | 结论 |
|---|---|---|
| unsloth | ❌ Triton | 弃用 |
| bitsandbytes(QLoRA) | ❌ CUDA | 弃用（bf16 LoRA） |
| flash-attn2/xformers | ❌ CUDA | 用 Twinkle 的 kernelize(NPU 内核) |
| **Twinkle** | ✅ 原生支持 Ascend | **采用为框架层** |
| MindSpeed-MM | ✅ 但无你的目标模型plugin | 备选（见 `cases/案例对比与问题分析.md`） |

## 6. 技术栈
```
CANN 驱动
  └─ torch-npu
       └─ Twinkle（TransformersModel + DeviceMesh + kernelize(NPU) + add_adapter LoRA）
            ├─ peft（LoraConfig）
            ├─ [本项目新增] TTSMultiCodebookProcessor + TTSMultiCodebookLoss
            └─ Dataset/Template（数据组件）
官方模型包（Qwen3TTSTokenizer / MOSS codec）→ 把音频编成 audio_codes
```

## 7. 探索路线图（阶段 0→3）

### 阶段 0：环境与基础设施
1. 装 CANN → torch-npu → `pip install twinkle-kit`（见 `twinkle-ascend-npu` skill）。
2. 验证：在文本 Qwen3 上跑通一个 Twinkle SFT cookbook（`cookbook/transformers/fsdp2.py`），证明 Twinkle+NPU 可用。
3. 装官方模型包（`qwen-tts`；`git clone OpenMOSS/MOSS-TTS`），下权重，跑通官方推理 demo。
4. 核实 MOSS 模型 HF 路径（401 问题）。
产出：`docs/07-昇腾环境与容器准备.md`（镜像选型+容器启动+验证步骤）；跑通的推理脚本。
新手提示：先"能合成声音"跑通，再碰训练。

### 阶段 1：数据准备
- 收集 15~30 分钟干净录音 → 去噪/VAD/切分 → ASR 转录+人工校对 → 官方 tokenizer 预编码为 audio_codes → manifest.jsonl（见 `tts-data-pipeline` skill + `docs/03` 录制标准 + `docs/09` 客户数据集分析）。
- **train≠dev**（拆 10~20% 不重叠句，文本不重复）——这是案例1"心里没谱"的反面教训。
- 客户已录制 162 条 WAV（48kHz/16bit/mono/50.5min），经 `scripts/analyze_dataset_quality.py` 分析：119条完全合格、30条SNR边界值需听辨、3条需删除，可用时长40.9~50.3min（详见 `docs/09`）。后处理 10 步清单见 `docs/09` §6。
- 录制标准见 `docs/03`（内部）/`docs/04`（客户版），新标准尚未传给客户，当前数据按旧标准录制。
产出：train/val manifest。

### 阶段 2：新增 TTS 组件 + LoRA SFT 训练（核心）
1. 为 Twinkle 新增 `TTSMultiCodebookProcessor`（把 manifest→训练样本，参考/文本 label 置 -100）与 `TTSMultiCodebookLoss`（多码本 next-token CE，镜像官方 `moss_tts_local_v1.5/finetuning/sft.py` 的 teacher-forcing；Qwen3-TTS 镜像其官方 `finetuning/` 脚本）。
2. 在文本 Qwen3 SFT 验证 Twinkle+NPU 后，接上 TTS 组件跑 Qwen3-TTS LoRA SFT。
3. 超参：lr 1e-4、alpha=2r、wd 0.1、betas(0.9,0.95)、cosine+warmup_ratio 0.03、epochs 3 起步（见 `tts-sft-npu`/`peft-lora-npu` skill）。**若训练数据"不自然"（非专业录制）**：用保守参数 r=8/alpha=16/epochs 2-3，降低 rank 让预训练自然韵律保留更多（见 `docs/09` §9 + `docs/02 §5` 微调能力边界）。
4. 先小数据 smoke-test 跑通，再全量。
产出：LoRA adapter；**TTS 组件 PR 回 modelscope/twinkle**。

### 阶段 3：评估与部署闭环
1. 评估：WER（内容准）+ 说话人相似度 SIM（音色像）+ UTMOS（好听）；对照零样本基线看收益；按 val WER 早停选 best。
2. 部署：合并或即挂 adapter → 用本地 `vllm-omni-tts-integration` skill 接入 vLLM-Omni serving。
产出：评估报告；可服务模型。

## 9. 风险与对策
| 风险 | 对策 |
|---|---|
| Twinkle 无 TTS 支持 | 阶段2 新增组件；先文本Qwen3 SFT 验证框架再接 TTS |
| 昇腾内核兼容 | 用 Twinkle 官方推荐版本；kernelize 报错可临时 TWINKLE_TORCH_BASELINE=1 |
| 过拟合训死音色 | train≠dev、低 lr/少 epoch、监控 val WER 早停、加 dropout |
| 案例多为 CUDA 栈 | 取其"数据/loss 逻辑"，用 Twinkle 重写 |
| MOSS 模型路径 401 | 阶段0 核实 org 名/是否 gated |
